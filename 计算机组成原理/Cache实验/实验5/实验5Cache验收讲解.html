1. 实验要做什么

这个实验的核心任务是：在实验包给好的 CPU / SoC 环境中，用 Verilog 实现 Cache 模块，让 CPU 的取指和数据访存请求先经过 Cache，再访问下一级存储。

一句话：Cache 位于 CPU 和内存之间，命中时直接返回数据，缺失时再去访问内存，从而减少慢速内存访问次数。

实验包已经给好了 MIPS CPU、类 SRAM 到 AXI 的转换桥、RAM、外设和仿真环境。我们主要补全 Cache 部分。

CPU / MIPS core
   |-- cpu_inst_*  取指接口
   |-- cpu_data_*  数据读写接口
        |
      cache.v
        |-- i_cache.v  指令Cache
        |-- d_cache.v  数据Cache
        |
   cache_inst_* / cache_data_* 访问下一级存储

3. 地址如何拆分

32位地址被拆成 tag、index、offset 三部分。

31          12 11          2 1      0
+-------------+-------------+--------+
|     tag     |    index    | offset |
+-------------+-------------+--------+
    20 bit        10 bit      2 bit
  • offset：一行是 1 个 word，4 字节，所以低 2 位表示字节偏移。
  • index：4KB / 4B = 1024 行，所以需要 10 位。
  • tag：32 位地址剩下 20 位。
直接映射怎么判断命中：先用 index 找到唯一一行，再看这一行 valid 是否为 1，并且 tag 是否等于请求地址的 tag。 
hit = cache_valid[index] && (cache_tag[index] == tag)

4. 类 SRAM 握手接口

CPU 侧和内存侧都使用类似 SRAM 的握手接口。以读请求为例：

信号方向含义
req请求方发出请求有效
addr请求方发出访问地址
addr_ok接收方返回地址已经被接收
data_ok接收方返回读数据有效，或写操作完成
rdata接收方返回读出的数据
验收说法：CPU 发 req，Cache 用 addr_ok 接收请求；如果命中，Cache 很快用 data_ok 返回；如果缺失，Cache 再向下一级存储发 cache_*_req，等下一级返回 cache_*_data_ok 后再返回 CPU。

5. 模块关系

cache.v 只是一个总包装，它内部实例化两个子模块：

cache.v
  |-- i_cache：处理 CPU 取指请求，只读
  |-- d_cache：处理 CPU 数据访问，读写都有

这样分开做的原因：

  • CPU 本来就有独立的指令接口和数据接口。
  • 指令 Cache 只读，不需要 dirty 和写回，逻辑简单。
  • 数据 Cache 需要处理 load/store、字节写、写回和替换，单独写更清楚。

6. 指令 Cache 怎么做

内部保存什么

cache_valid[index]：这一行是否有效
cache_tag[index]  ：这一行对应的 tag
cache_block[index]：这一行保存的 32 位指令

状态机

S_IDLE等待 CPU 取指请求，判断是否命中。
命中直接返回 cache_block[index]。
缺失保存地址信息，进入 S_REFILL。
S_REFILL向下一级存储读数据，返回 CPU 并填入 Cache。

指令 Cache 不需要 dirty 位，因为 CPU 不会通过取指接口修改指令 Cache 内容。

口头回答：指令 Cache 是只读直接映射 Cache。命中时直接返回，缺失时从下一级存储取一个 word，返回 CPU 的同时写入 Cache，并更新 valid 和 tag。

7. 数据 Cache 怎么做

数据 Cache 要处理读和写，所以比指令 Cache 多了 dirty 位。

cache_valid[index]：这一行是否有效
cache_dirty[index]：这一行是否被 CPU 修改过但未写回
cache_tag[index]  ：这一行对应的 tag
cache_block[index]：这一行保存的数据

状态机

S_IDLE等待 CPU load/store，判断命中。
S_WRITEBACK缺失且旧行 dirty 时，先把旧行写回内存。
S_REFILL从内存读新数据，填入 Cache。

四种情况

情况处理
读命中直接返回 cache_block[index]，不访问内存。
写命中合并写数据到 Cache，dirty = 1，不马上写内存。
读缺失如果旧行 dirty 先写回，再从内存读新数据并填入 Cache。
写缺失写分配：先读入新块，再合并 CPU 写数据，填入 Cache，dirty 置 1。

8. 字节写、半字写和 dirty

为什么需要 merge

CPU 可能执行 sb、sh、sw，分别写 1 字节、2 字节、4 字节。但 Cache 中一行是 32 位 word。写 1 字节时，不能把整个 word 覆盖掉。

旧数据：32'h11223344
地址低两位：2'b01
写 1 字节：8'hAA
结果：32'h1122AA44

所以代码中用 merge_write_data 根据 size 和 addr[1:0] 生成字节掩码，只改对应字节。

dirty 位的意义

本设计是写回策略。写命中时只修改 Cache，不立刻修改内存，所以 Cache 和内存暂时不一致，需要设置 dirty 位。以后这行被替换时，再写回内存。

写回地址：被替换的旧行地址由 {victim_tag, saved_index, 2'b00} 拼出来。不能用新地址，因为要写回的是旧 Cache line。

9. saved 信号为什么重要

Cache 缺失不是一个周期完成的。CPU 请求被接收后，请求信号可能撤掉，但后续 writeback/refill 还需要知道原请求的信息，所以必须保存。

信号作用
saved_wr保存原请求是读还是写。
saved_size保存写大小，支持字节/半字/字写。
saved_addr保存原访问地址。
saved_wdata保存 CPU 要写的数据。
saved_tag / saved_index保存新数据填入 Cache 的位置。
victim_tag / victim_data保存被替换的旧行，用于 dirty 写回。
验收回答：缺失处理要跨多个周期，如果不锁存请求信息，后续状态就不知道原来要访问哪个地址、写什么数据、写几个字节。

10. 为什么要加板级顶层 cache_board_top

之前直接把 cache 设为 Vivado 顶层时，Place 阶段报错 IO 超限：

IO Placement failed due to overutilization.
This design contains 373 I/O ports while the target device contains only 210 available user I/O.

原因是：cache 是 SoC 内部模块，有 CPU 侧和内存侧大量内部接口。如果把它当 FPGA 顶层，Vivado 会以为这些接口都要接到真实引脚上。

解决方式是添加 cache_board_top.v：

  • 只暴露真实板级 IO：clk、rst、led[15:0]。
  • 内部实例化 cache。
  • 内部用一个小状态机模拟 CPU 请求和内存响应，对 Cache 做自测。
LED含义
LED0自测完成
LED1自测通过
LED[7:2]错误码低位
LED[15:8]状态和错误码高位
板级 bitstream 验证的是 Cache 自测外壳，不是完整 SoC 上板。完整 SoC 正确性通过 trace 仿真验证。

  1. 实验要做 CPU 和内存之间的 Cache。
  2. 我把 Cache 分成 i_cache 和 d_cache。
  3. 两个 Cache 都是 4KB 直接映射，1 word 一行。
  4. 地址拆成 tag/index/offset，index 找行，tag 判断命中。

13. 助教可能问的问题和回答

Q1：什么是直接映射 Cache？

一个内存块只能映射到 Cache 中唯一一行，这一行由 index 决定。访问时用 index 找行，再比较 tag 判断是不是目标地址。

Q2：为什么需要 tag？

很多不同地址可能有相同 index，会映射到同一行。tag 用来区分这一行当前保存的是哪个内存块。

Q3：为什么需要 valid 位？

复位后 Cache 内容无效，即使 tag 碰巧相等也不能算命中。valid 表示这一行是否保存了合法数据。

Q4：为什么数据 Cache 需要 dirty 位？

因为采用写回策略。写命中只修改 Cache，不马上写内存，所以 dirty 用来标记“Cache 中数据比内存新”。替换前必须写回。

Q5：写回和写直达有什么区别？

写直达每次写 Cache 都同时写内存；写回只在 dirty 行被替换时写内存。写回减少内存写次数，但需要 dirty 位和写回状态。

Q6：什么是写分配？

写缺失时先把目标地址所在内存块读入 Cache，再在 Cache 中完成写操作。本设计的数据 Cache 使用写分配。

Q7：指令 Cache 为什么没有 dirty 位？

指令 Cache 只处理取指读请求，不处理写请求，所以不会出现 Cache 被 CPU 修改但内存没更新的情况。

Q8：缺失时为什么要保存 saved_addr、saved_wdata？

缺失处理要多个周期，CPU 请求信号不一定一直保持。保存后，状态机后续仍知道原来的地址、写数据和写大小。

Q9：写回旧行时地址怎么生成？

用旧 tag、当前 index 和 2 位 0 offset 拼出：{victim_tag, saved_index, 2'b00}。不能用新地址，因为写回的是被替换的旧行。

Q10：addr_ok 和 data_ok 有什么区别？

addr_ok 表示请求地址被接收；data_ok 表示读数据有效或写操作完成。两者可能不是同一周期。

Q11：命中时为什么可以马上 data_ok？

命中时数据已经在 Cache 内部，不需要访问下一级存储，所以可以直接返回。

Q12：字节写为什么不能直接覆盖整个 word？

因为 sb 或 sh 只修改部分字节，其他字节必须保留。直接覆盖会破坏不该修改的数据。

Q13：为什么 Vivado 之前 IO 超限？

因为把内部模块 cache 当成 FPGA 顶层，Vivado 把它的 CPU 侧和内存侧接口全当外部引脚，超过芯片 IO 数量。改用 cache_board_top 后只暴露时钟、复位和 LED，就能实现。

Q14：怎么证明 Cache 是正确的？

单元测试验证命中、缺失、字节写、dirty 写回；SoC trace 仿真跑完测试程序并 PASS；Vivado 对板级顶层完成 bitstream，DRC 0 错误且时序满足。

Q15：这个设计有什么局限？

直接映射冲突缺失较多；一行只有 1 个 word，空间局部性利用少；没有实现组相联、LRU 或 AXI burst。这些可以作为后续优化方向。

14. 一分钟口头总结

本实验实现了 CPU 和下一级存储之间的 Cache 模块。我的 cache.v 分成 i_cache 和 d_cache。两者都是 4KB 直接映射 Cache，一行 1 个 word，地址拆成 20 位 tag、10 位 index 和 2 位 offset。指令 Cache 只读，命中直接返回，缺失进入 refill 从内存取数并填入 Cache。数据 Cache 采用写回和写分配策略，命中读直接返回，命中写只修改 Cache 并置 dirty；缺失时如果旧行 dirty，先 writeback，再 refill。字节写通过 merge_write_data 按 size 和地址低两位只改对应字节。工程通过了 Cache 单元测试、SoC trace 仿真和 Vivado bitstream 生成。之前 IO 超限是因为把内部 cache 当顶层了，后来加了 cache_board_top 板级自测顶层，只暴露时钟、复位和 LED，所以可以在 xc7a100tcsg324-1 上生成 bitstream。
