# RBAC 权限管理系统 · 操作效率改良方案

> 对象：`rbac-cli`（实验二）
> 目标：在不破坏现有分层/代理/审计与命令行可脚本化能力的前提下，把高频管理操作的**输入次数、认知负担和出错成本**显著降下来。
> 原则：**增量改造**（旧路径保留，新路径增强）、**脚本零破坏**（现有 18 个在用回归脚本不改也能过）、**不引入第三方 UI 库**。

---

## 1. 现状评估结论（问题量化）

| 问题 | 现状表现 | 影响 |
|---|---|---|
| 靠背 ID 定位 | 修改/删除/分配/启停/重置全部要求手输数据库 ID，ID 只有列表里能看到 | 每次操作前要"去列表查 ID → 回来输入"，来回切换 |
| 表单一次成型 | 新增用户 5 个字段全部填完才校验，邮箱错一个字符则全部重填 | 单次录入成本翻倍，最影响日常使用 |
| 授权靠扫表手拼 | 给角色授权要扫 33 行权限表，手敲 `7,8,10,19...` | 选项多、易错、无法按类型/前缀批量选 |
| 查询表单固定 5 题 | 审计查询每次都要过 模块/用户/结果/起止时间 5 个提示；模块名必须精确匹配 | 看最新日志也要敲 5 次回车；输错模块名静默返回全部 |
| 取消语义不统一 | 菜单 `b/q` 有效；字段里 `q` 会写进字段，`readOptional/readOptionalInt` 里 `b` 不取消 | 新手误操作后得到莫名其妙的结果 |
| 无批量能力 | 多选删除/批量分配角色都不支持 | 用户多时逐条重复劳动 |
| 同一对象连续操作代价高 | 对同一用户做"分配角色→启停→重置密码"要三次回到菜单并三次输入 ID | 每次操作都要重新定位对象 |

**量化基线（当前实现，按"输入行数"计）**

| 场景 | 当前输入次数 | 备注 |
|---|---|---|
| 查看用户列表 | 4 | 模块→列表→关键字回车→状态回车 |
| 新增用户（含 1 次邮箱格式错误） | 14 | 7 + 整表重填 7 |
| 对同一用户做 3 项操作 | 16 | 含 1 次查 ID 往返 + 3 次重输 ID |
| 给角色分配 10 个权限 | 5（但需扫 33 行、手拼 ID 串） | 认知成本高 |
| 审计"看最近失败登录" | 8 | 模块→查询→5 个条件→翻页返回 |

## 2. 方案总览

| 编号 | 能力 | 解决的问题 | 优先级 | 预计改动 |
|---|---|---|---|---|
| A | **对象工作台**（列表选序号 → 详情 + 操作闭环） | 背 ID、来回导航、同对象重复定位 | P0 | `AbstractScreen`、`UserScreen`、`RoleScreen` |
| B | **统一输入语义 + 快捷键图例** | b/q/空 语义混乱 | P0 | `ConsoleReader`、`AbstractScreen`、各 Screen 提示 |
| C | **表单逐字段校验（只重填错误项）** | 校验失败全量重填 | P0 | `BusinessException`、`UserServiceImpl`/`RoleServiceImpl`、`UserScreen`/`RoleScreen` |
| D | **审计查询提速**（模块选择器/时间预设/失败日志入口/条件记忆） | 固定 5 题、精确匹配 | P0 | `AuditScreen`、`AuditLogDao`（模糊匹配） |
| E | **授权表达式 + 树形选择 + 变更预览** | 扫表手拼、易错 | P1 | `RoleScreen`、新增 `SelectionExpression` 解析器 |
| F | **批量操作**（多选用户批量启停/分配角色） | 无批量、逐条重复 | P1 | `UserScreen`、`AbstractScreen` |
| G | **结果摘要与空态引导** | 看不到"改了什么"、空列表无指引 | P1 | `UserScreen`/`RoleScreen`/`AbstractScreen` |
| H | 全局帮助页 `?`、上次登录名回填 | 锦上添花 | P2 | `MenuEngine`、`LoginScreen` |

> 明确不做：raw-key 全屏 TUI（Lanterna 等）。原因：会破坏 stdin 脚本回归与"逐行可测"的工程优势，且课程要求是"命令行交互"而非全屏应用。也不做"纯命令语言"（kubectl 式），因为演示场景下可发现性更重要。本方案采用"数字菜单 + 对象工作台 + 表达式"的混合形态。

## 3. 详细设计

### 3.1 对象工作台（A）

**交互流程（以用户为例）**

```
» 请输入选项编号： 1                     ← 用户管理
  ▌ 用户列表（分页/条件查询）
  关键字（回车跳过）：                     ← 回车
  状态过滤（1 启用 / 0 禁用，回车全部）：   ← 回车
  ┌────┬────┬────────────┬────────────┬──────┬──────┬────────────┐
  │ 序号│ ID │ 用户名     │ 姓名       │ 状态 │ 角色 │ 创建时间   │
  ├────┼────┼────────────┼────────────┼──────┼──────┼────────────┤
  │ 1  │ 1  │ admin      │ 超级管理员 │ 启用 │ 超管 │ 2026-10-20 │
  │ 2  │ 5  │ user1      │ 张三       │ 启用 │ 普通 │ 2026-10-20 │
  └────┴────┴────────────┴────────────┴──────┴──────┴────────────┘
  输入序号进入操作（n/p 翻页，g3 跳到第3页，#5 按ID，b 返回）： 2

  ╭─ 用户工作台 · user1 ────────────────────────────── 主菜单 / 用户管理 ─╮
  │ ● user1（张三）  状态：启用  角色：普通用户  失败次数：0  未锁定      │
  ├─ 对该用户的操作 ─────────────────────────────────────────────────────┤
  │  1  查看/修改资料        2  分配角色                                  │
  │  3  启用/禁用            4  重置密码                                  │
  │  5  删除用户                                                          │
  │  0  返回用户列表                                                      │
  ╰───────────────────────────────────────────────────────────────────────╯
  · 输入编号执行操作                                      · b 返回 · q 退出
```

- 在工作台里做完一项操作会自动**重新查询并重绘**详情（状态/角色立刻刷新），可连续操作同一对象，不再重输 ID。
- 删除成功后自动回到列表（对象已不存在）；返回码 `0` 回列表，`b` 逐级返回。
- 工作台按钮按当前用户权限**动态隐藏**（复用 `LoginUser.hasPermission`），无权限的入口不出现，避免"点了才报错"。
- 列表页仍保留 `#<ID>` 输入作为兜底（老用户/脚本可用），`n/p` 翻页，`g<页码>` 跳页；数字的语义在提示行中明确写出。

**实现要点**

1. `AbstractScreen` 新增泛型方法：
   ```java
   protected <T> T browseAndSelect(String title, String itemName, String[] headers,
                                   Function<Integer, PageResult<T>> loader,
                                   Function<T, String[]> rowMapper,
                                   BiFunction<T, Integer, String[]> indexedRowMapper)
   ```
   行首插入"序号"列（当前页内 1..N），翻页后序号重新编号；返回被选中的记录或 `null`（取消）。
2. `readPageCommand` 拆分为两种模式：
   - 只读列表（审计）：`n/p/数字跳页/b`（保持现状）
   - 可选列表：`数字=选行`、`n/p`、`gN` 跳页、`#ID` 按 ID 选择、`b` 返回
3. `UserScreen` / `RoleScreen` 新增工作台：
   ```java
   private void listUsers() { ... while (true) { UserVO sel = browseAndSelect(...); if (sel == null) return; workbench(sel.getId()); } }
   private void workbench(Long id) {
       Menu menu = new Menu("用户工作台 · " + user.getUsername());
       // 右侧面包屑由引擎自动拼接
       menu.add("1", "查看/修改资料", () -> updateUser(id));
       ...
       engine.run(menu);   // 需要把 MenuEngine 传入 Screen（构造参数）
   }
   ```
   > 目前 `UserScreen` 只持有 printer/reader/locator；工作台需要嵌套菜单，构造时增加 `MenuEngine` 参数（`MainScreen` 已经这样传）。
4. 现有方法（`createUser/updateUser/...`）内部原本会 `readLongRequired("用户 ID")`，改造为：
   - 保留 `updateUser()`（读 ID 后调 `doUpdate(id)`）——旧菜单入口不变；
   - 新增 `doUpdate(Long id)` 供工作台复用。

**收益**：对同一用户做 3 项操作从 16 次输入降到约 9 次，且无 ID 记忆负担；高频路径从"菜单→操作"变成"列表→对象→操作"，与 `kubectl get→describe→act`、`gh` 交互惯例一致。

### 3.2 统一输入语义 + 快捷键图例（B）

| 输入场景 | `b` | `q` | 空回车 | `?` |
|---|---|---|---|---|
| 菜单编号 | 返回上级 | 退出程序 | 忽略（重绘） | 显示帮助页（P2） |
| 需要输入对象的提示（ID/序号/字段编辑/密码确认） | **取消当前操作** | 退出程序 | 按提示取默认/保持 | 显示该提示取值说明 |
| 搜索/过滤词（关键字、用户名、资源编码） | 作为普通文本 | 作为普通文本 | 默认值 | 普通文本 |

- `ConsoleReader` 增加统一入口：
  ```java
  public String readLine(PromptMode mode, String prompt, String defaultValue)
  // PromptMode.TEXT（不拦截）/ OPERATION（b 取消、q 退出）/ NUMBER / PASSWORD / OPTIONAL
  ```
  `readLongRequired/readField/confirm` 内部统一走 `OPERATION` 模式；`readOptional` 用于搜索词保持 `TEXT`。
- 每个动作页开头打印一行图例（灰色）：
  `· 提示：b 取消当前操作 · q 退出程序 · 回车使用默认值`
  只在**操作类**页面显示，列表/搜索页显示对应说明，避免污染输出。
- 风险与兼容：现有脚本全部是合法输入，不受影响；字段里真正需要输入字母 `b`（如用户名 `bob`）不受影响（因为只在整行等于 `b` 时取消）。

### 3.3 表单逐字段校验（C）

**目标**：错误只重填一项，已输入内容保留。

**交互示例**

```
  ▌ 新增用户
  用户名： zhangsan
  密码： ······
  姓名： 张三
  邮箱： zhangsan_at_example.com
  ! 邮箱格式不正确（如 user@example.com），请重新输入
  邮箱： zhangsan@example.com
  电话（回车跳过）：
  √ 创建用户 [zhangsan] 成功
```

**实现要点**

1. `BusinessException` 增加可选字段定位：
   ```java
   public class BusinessException extends RuntimeException {
       private final String code;
       private final String field;   // 新增：出错的字段名（username/password/email/phone/...）
   }
   ```
2. `UserServiceImpl.create/update` 的字段校验改为逐项抛出带 `field` 的异常（`ValidateUtil` 增加 `requireNonBlank(field, ...)` 重载）。
3. 屏幕层提交循环：
   ```java
   while (true) {
       try { userService.create(dto); break; }
       catch (BusinessException e) {
           if (!refill(dto, e.getField())) throw e;   // 无法定位字段则交回引擎
       }
   }
   private boolean refill(UserDTO dto, String field) {
       switch (field) {
           case "username": dto.setUsername(askUsername()); return true;
           case "email":    dto.setEmail(askEmail());       return true;
           ...
           default: return false;
       }
   }
   ```
   唯一性冲突（`用户名已存在`）同样带 `field=username`，只重问用户名。
4. 密码确认不一致：只重读"确认新密码"，不回退新密码。
5. 兼容：合法输入的交互序列不变（脚本零改动）；仅错误路径变化。

### 3.4 审计查询提速（D）

**改动点**

1. **模块选择器**：把自由文本改成"编号 + 名称 + 回车全部"：
   ```
   模块（1 认证 / 2 用户管理 / 3 角色管理 / 4 权限管理 / 5 资源管理 / 6 审计管理 / 7 权限校验 / 8 个人中心，回车全部）： 1
   ```
   输入名称（如"认证"）仍然接受——脚本 `w_audit_filter.txt` 不受影响。
2. **结果筛选**：接受 `s/f/1/0/回车`；非法输入**明确提示重试**（不再静默忽略）。
3. **时间预设**：`1=今天 2=最近7天 3=最近30天`，其余按 `yyyy-MM-dd[ HH:mm]` 解析。
4. **新增快捷入口**（只增不改菜单编号）：
   - `4  失败日志（最近 20 条）`：`result=FAILURE` 直查，一次回车出结果；
   - `5  快速查询（最近 20 条）`。
5. **条件记忆**：在 `cli` 层增加会话级 `UiState`（保存上次审计条件），提示"回车沿用上次条件：[认证 / 张三 / 失败 / 2026-10-01~2026-10-20]"。
6. **DAO 微调**：`AuditLogDao.findPage` 的 module 改为 `LIKE ?`（`%模块%`），并增加 `findPageByResult` 便捷方法；同步更新 `countByCondition`。

**收益**："看最近失败登录"从 8 次输入降到 2 次（`6` → `4`）。

---

### 3.5 授权表达式 + 树形选择 + 变更预览（E，P1）

**展示**：把现在的"平铺表格"换成树形缩进（复用 `PermissionService.tree`），层级用缩进表达，去掉"父权限ID"列：

```
  ├─ 用户管理（menu:user）
  │    7  user:list          查询用户
  │    8  user:create        新增用户
  │    ...
  ├─ 权限管理（menu:permission）
  │   19  permission:list    ...
```

**输入语法**（`SelectionExpression` 解析器，独立类 + 用例表）

| 写法 | 含义 |
|---|---|
| `7,8,10` / `7 8 10` | 直接给出 ID（兼容现状） |
| `7-13` | ID 区间（含两端） |
| `user:*` | 该前缀下全部权限 |
| `@menu` / `@op` / `@res` | 按类型全选（菜单/操作/资源） |
| `+5` / `-10` | 在现有集合上增/删 |
| `0` | 清空 |
| `all` | 全部（需二次确认） |

**变更预览**：解析后展示 `新增 3 项 / 移除 1 项 / 最终 12 项` 并列出明细，确认后才提交（降低误操作）。

**实现**：
- 新增 `cli/console/SelectionExpression.java`（纯函数：`parse(String expr, List<Permission> all, Set<Long> current) → SelectionResult`），可单测（jshell 用例表）。
- `RoleScreen.assignPermissions` 与 `UserScreen.assignRoles` 复用同一解析器。
- 服务层签名不变（仍提交 `List<Long>`），审计/事务链路不动。

---

### 3.6 批量操作（F，P1）

- 用户列表支持多选：`1,2,5`（复用 `SelectionExpression` 的 ID 列表部分，序号同样支持 `1-3`）。
- 选中后进入"批量菜单"：批量启用/批量禁用/批量分配角色/批量删除。
- 逐条调用服务（保持**每条操作独立审计**，权限校验逐条生效），汇总结果：
  ```
  · 批量结果：成功 4 条，失败 1 条（user3：内置超级管理员账号禁止禁用）
  ```
- 删除/禁用等危险操作仍需一次总确认 + 列出对象清单。

---

### 3.7 结果摘要与空态引导（G，P1）

- 更新类操作回显差异：`√ 已更新用户 [user1]：邮箱 - → user1@example.com；状态 启用 → 禁用`（由屏幕层比较前后值生成，服务层不改）。
- 空列表给出下一步建议：`! 没有符合条件的用户 · 可输入 2 新增用户，或 b 返回调整条件`。

## 4. 验收标准

### 4.1 硬性要求

1. **现有 18 个在用回归脚本零修改全部通过**（`test\` 下的 stdin 脚本 + `scan.py` 的 √/×/! 判定；`b1b`、`g_cache_cleanup` 为历史修复版，不纳入验收基线）。
2. `test\check_ui.py` 对齐检查通过（面板 78 列、表格块内一致）。
3. 越权拦截、删除保护、登录锁定、缓存失效、事务回滚等既有断言继续通过。
4. 审计记录不受影响：新增字段定位不改变方法签名与注解，审计仍记录模块/操作/对象/结果/耗时。
5. 新增功能有对应脚本（建议 6 个）：

| 新脚本 | 覆盖 |
|---|---|
| `y1_user_workbench.txt` | 列表选序号 → 工作台连续 3 项操作 → 返回 |
| `y2_field_refill.txt` | 邮箱错误 → 只重填邮箱 → 创建成功 |
| `y3_audit_quick.txt` | 失败日志快捷入口 + 时间预设 |
| `y4_perm_expr.txt` | `user:*`、`7-13`、`+`/`-`、变更预览 |
| `y5_batch_users.txt` | 多选批量禁用/启用 + 部分失败汇总 |
| `y6_cancel_semantics.txt` | 字段内 b 取消、q 退出、空默认 |

### 4.2 效率指标（实施后实测）

| 场景 | 现状 | 目标 |
|---|---|---|
| 对同一用户做 3 项操作 | 16 次输入 | ≤ 9 次，且 0 次 ID 记忆 |
| 新增用户（1 次邮箱错误） | 14 次输入（整表重填） | ≤ 8 次（仅重填邮箱） |
| 给角色分配 10 个权限 | 手拼 10 个 ID | ≤ 3 个表达式片段（如 `user:* role:list -10`） |
| 看最近失败登录 | 8 次输入 | 2 次输入 |
| 批量禁用 5 个用户 | 不支持（约 20 次） | 4 次输入 |

## 5. 实施步骤（按批交付，可独立验收）

### 批次 1：输入语义 + 对象工作台 + 字段校验（P0-A/B/C）
1. `ConsoleReader` 统一 `PromptMode`，`AbstractScreen.readField/confirm` 接入；动作页图例。
2. `AbstractScreen.browseAndSelect` + `readPageCommand` 双模式；`UserScreen`/`RoleScreen` 列表改造。
3. `UserScreen`/`RoleScreen` 工作台（`MenuEngine` 注入、按钮按权限隐藏、操作后刷新）。
4. `BusinessException.field` + 服务端字段标记 + 屏幕重填循环。
5. 编译 → `check_ui` → 18 个旧脚本 → 新增 `y1/y2/y6` → 交互计数实测。

### 批次 2：审计提速 + 授权表达式 + 批量（P0-D / P1-E/F）
6. 审计：模块选择器、结果/时间预设、失败日志入口、条件记忆、DAO 模糊匹配。
7. `SelectionExpression` 解析器 + 用例表（jshell）。
8. 授权界面树形化 + 变更预览；角色/用户分配共用。
9. 用户列表多选 + 批量菜单 + 结果汇总。
10. 新增 `y3/y4/y5` → 回归全跑。

### 批次 3（可选）：全局帮助页 `?`、上次登录用户名回填、操作摘要（G/H）。

**预计工作量**：批次 1 约 8 个文件、400 行；批次 2 约 6 个文件、450 行；批次 3 约 120 行。均不触碰 `jdbc/dao/service 的既有签名`（除 `BusinessException` 加字段、Audit DAO 加/改查询方法）。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 数字语义冲突（列表里数字既可能"跳页"又可能"选行"） | 明确规则并在提示行写死：可选列表=选行（`gN` 跳页），只读列表=跳页 |
| 改造导致回归脚本失效 | 旧菜单项与旧输入序列全部保留（工作台是新增层级，不改既有键位）；执行"18 脚本零改动"验收 |
| 工作台内对象被并发删除/禁用 | 每次进入工作台前重新查询；查询失败提示后返回列表 |
| 表格加"序号"列后过宽 | 复用表格自动压缩（≤112 列）+ `run.bat` 120 列窗口 + `check_ui.py` 校验 |
| 服务端新增字段标记影响审计 | 仅新增字段与重载，不改方法签名/@AuditLog/@RequiresPermission |
| 表达式误选大量权限 | 变更预览 + `all` 二次确认 |

---

## 7. 结论

- 本方案不改技术栈、不动分层与设计模式落地点，只重构**表现层的输入与导航模型**，因此对课程评分点（JDBC、动态代理、设计模式、注解、泛型等）零影响，反而能把"用户体验设计"写进实验报告的创新点。
- 优先做批次 1：它覆盖了 80% 的日常摩擦（ID 记忆、整表重填、取消语义），且风险最低、可当天验证。
- 批次 2 的表达式与批量是"从能用到好用"的分水岭；批次 3 属锦上添花。
